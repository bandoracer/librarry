# Librarry product and reliability audit — 2026-09-15

Reviewed checkout: `6c1f32ed1c916e8077040f9ded3a44d1bd07868e`.

## Assessment

The foundation is worth developing. Librarry has real acquisition integrations, a coherent feature-based React UI, explainable release decisions, provider identity tracking, a scheduler, and working database backups. Its main weakness is correctness across workflow boundaries: download to file, scan to existing record, configuration to deployed container, and query state to UI membership. Those boundaries need a stabilization release before wider promotion or unattended migration from Readarr.

This was a review, not a deployment or repair. No production configuration, library files, download jobs, or GitHub discussions were changed. Live activity was limited to reads and searches. Temporary test programs and fixtures were kept outside the repository using Go overlays. Local audit servers and browser tabs were closed afterward.

## Priority findings

### 1. P1 — Missing download payloads can import an unrelated book

**Confirmed with a local filesystem reproduction.** `locateDownloadSource` first tries `savePath/name`, then falls back to recursively searching all of `savePath`. `bestBookFile` chooses the largest supported file. If the intended payload is missing or its name differs, another download in the shared category folder can be selected.

For a wanted-linked download, `Import` then replaces the inferred title/author with the wanted record and can mark that book imported. This can mislabel an unrelated file and falsely satisfy a wanted item.

Evidence: `backend/internal/library/service.go:2419`, `:2448`, `:459`, and `:656`. The audit fixture contained only `Unrelated Book.epub` while the requested download was named `Missing Book`; the function returned the unrelated file without error.

**Acceptance:** derive the exact payload from download-client content/file information; never search sibling downloads as a fallback. Missing or ambiguous payloads must enter review without marking success.

### 2. P1 — Multipart audiobooks are treated as one file, then the entire download can become eligible for deletion

**Single-file selection reproduced; cleanup consequence established by code inspection.** A folder containing `01.mp3`, `02.mp3`, and `03.mp3` returns only the largest chapter. Completed import records one file and marks the whole download imported. The cleanup worker deletes imported, stopped/paused completed torrents with `DeleteFiles: true`.

This can retain one chapter and remove the remaining source chapters once the cleanup condition is met. Multi-book packs have the same structural problem. No destructive end-to-end test was performed and no existing data loss is asserted.

Evidence: `backend/internal/library/service.go:572`, `:694`, `:2448`; `backend/cmd/librarry/main.go:614`.

**Acceptance:** represent and import the full file set, preserve chapter order and names, and require verified completeness before cleanup. Unsupported packs should require review.

### 3. P1 — A library rescan discards import linkage

**Confirmed code path; not exercised on production.** `Scan` constructs a fresh file record from disk. That record lacks `wantedId`, `downloadId`, import provenance, and Calibre handoff metadata. `UpsertFile` handles a path conflict by assigning `metadata = excluded.metadata`, replacing the previous metadata wholesale.

Book presence and acquisition eligibility depend on `files.metadata->>'wantedId'`. A routine scan can therefore sever the link to an existing imported book, change its displayed state, and allow another grab for records still in the `wanted`/`grabbed` lifecycle. This also violates the expectation that provider or local evidence cannot erase operator-established identity.

Evidence: `backend/internal/library/service.go:383`, `:2073`; `backend/internal/library/store.go:55`; `backend/internal/wanted/store.go:355`, `:1960`.

**Acceptance:** keep stable linkage in explicit fields or preserve authoritative metadata separately from scan evidence. Scan an imported fixture twice and verify that identity, presence, provenance, and acquisition eligibility remain unchanged.

### 4. P1 — Audiobook release search is broken against the live integration

**Confirmed live and locally.** A native release search for Moby Dick with `format: audiobook` returned HTTP 502 and `prowlarr search returned 400 Bad Request`. The adapter sends `categories=7000,3030` as one parameter; the Prowlarr JSON API expects repeated category parameters. Ebook searches use only one category, masking the bug.

The existing [community PR #2](https://github.com/bandoracer/librarry/pull/2) addresses this exact defect and includes a regression test. It is mergeable, but has no successful check attached in the PR readback. Its failed Actions run no longer yielded retrievable logs, so the reason was not established.

Evidence: `backend/internal/acquisition/prowlarr.go:125`.

**Acceptance:** review and validate that contribution; test ebook, audiobook, and any-format search independently, retaining Newznab's different feed parameter convention.

### 5. P1 — Documented import/cleanup switches are not passed into Docker containers

**Confirmed using `docker compose config`.** The example environment advertises `LIBRARRY_COMPLETED_IMPORT_ENABLED`, `LIBRARRY_COMPLETED_IMPORT_MODE`, and `LIBRARRY_COMPLETED_REMOVE_ENABLED`. The deployment templates explicitly enumerate environment variables but omit these controls. Setting import and removal to false outside Compose does not put them in the API container environment.

The Go defaults enable completed imports and removal. An operator can believe automatic cleanup is disabled while it remains enabled. Related settings are also absent across the generic, source-build, TrueNAS, and Unraid templates.

Evidence: `deploy/.env.example`, `deploy/docker-compose.yml`, `deploy/docker-compose.build.yml`, `deploy/truenas/install.yaml`, `deploy/unraid/docker-compose.yml`; `backend/internal/config/config.go:156`.

**Acceptance:** validate a shared configuration contract across all deployment variants. Test disabling each advertised automation and verify the effective container and runtime configuration. Reconcile README examples and Compose fallback defaults with the intended auto-grab policy.

### 6. P1 — Authentication can fail open when the database URL is omitted

**Reproduced with an isolated process.** Started the current binary on localhost with forms authentication and test credentials, but no database URL. Startup logged `api authentication enabled`. Unauthenticated `/api/v1/auth/status` nevertheless returned `{"authenticated":true,"method":"none"}`, and API reads succeeded.

`effectiveAuthMethod` intentionally falls back to none when persistence is unavailable. A configured-but-unreachable database exits at startup instead, so this finding specifically concerns missing persistence configuration, not any database outage. The standard Compose template requires a database URL, reducing exposure through that installation route.

Evidence: `backend/internal/api/auth.go:90`; `backend/cmd/librarry/main.go:160`.

**Acceptance:** reject startup or protected operations when authentication is requested but cannot be enforced. Make security state explicit in readiness. The live LAN installation currently has method none; its outer access boundary was not audited.

### 7. P1 — Hardcover needs implementation work as well as credentials

**Code inspection plus a reproduced error-handling failure.** The intended primary metadata adapter immediately returns no results for author searches, does not populate an Edition, and does not map rich fields such as description, series, publication date, or ISBNs. It reports ready whenever a token string exists, and advertises backend rate limiting although no limiter is implemented in the metadata package.

A mocked HTTP 200 GraphQL response containing an authentication error was treated as a successful empty result. Failures can therefore look like missing books instead of provider errors.

The [official Hardcover search guide](https://github.com/hardcoverapp/hardcover-docs/blob/main/src/content/docs/api/guides/Searching.mdx) documents author search and rich book fields. Validate the actual response shape with recorded provider fixtures before advertising coverage. No valid live token was available; live schema compatibility is unverified.

Evidence: `backend/internal/metadata/providers.go:46`, `:71`, `:118`, `:144`. The existing provider adapter test file covers Open Library, not this contract.

**Acceptance:** implement the intended provider capabilities, surface GraphQL errors, distinguish configured from healthy, and add contract fixtures plus a controlled real-token qualification.

### 8. P2 — Runtime integration settings have a data race

**Confirmed by a targeted race-detector test.** `Reconfigure` overwrites the entire acquisition service with `*s = *next` while handlers and workers read configuration and client pointers without synchronization. Concurrent `Reconfigure` and `IntegrationConfig` calls produced a race warning. The original race suite passes because it does not exercise this interaction.

Evidence: `backend/internal/acquisition/service.go:87`, `:94`.

**Acceptance:** atomically swap immutable configuration/client snapshots or synchronize access. Exercise updates concurrently with health, list, and acquisition operations.

### 9. P2 — Query callback arguments corrupt wanted-view selection

**Reproduced using the installed TanStack Query implementation.** `useWanted` supplies `fetchWanted` directly as `queryFn` through `withDemoFallback`. Query calls it with a context object, which the fetcher interprets as its optional `view` argument. The request becomes `/api/v1/wanted?view=%5Bobject+Object%5D`, and the truthy argument bypasses terminal-status filtering.

This explains why removed entries are still visible in the live Library. Fixing only the wrapper would introduce another problem: the fetcher's default filter removes imported books too, while Library and Book pages share that data source. Define separate library and wanted-gap membership contracts before repairing the callback.

Evidence: `web/src/lib/queries.ts:110`, `web/src/lib/demo.ts:23`, `web/src/lib/api.ts:1532`. The isolated reproduction returned wanted/removed/imported through Query versus only wanted on a direct fetch call.

**Acceptance:** test removed-item behavior, completed-book visibility, detail routes, and search tracked badges using the same query integration used by the app.

### 10. P2 — Real libraries silently exceed list limits

**Confirmed in query/API implementation.** The main wanted list returns at most 200 rows with no paging parameters. The cutoff view also examines only 200 linked wanted items. File lists default to 200 and cap at 500; the scan defaults to 1,000 and tops out at 5,000 with no resume cursor. Repeating a scan revisits the beginning of the tree.

UI totals and local filtering operate on these partial datasets. Books can disappear from library/detail views as a collection grows, and a large import can appear complete while remaining incomplete.

Evidence: `backend/internal/wanted/store.go:268`, `:314`; `backend/internal/library/store.go:81`; `backend/internal/library/service.go:383`; `web/src/features/library/LibraryPage.tsx:136`.

**Acceptance:** server-side paging/filtering with accurate counts, direct detail lookup, resumable scans, and a fixture exceeding each current boundary.

### 11. P2 — Operational status and release evidence are misleading

`compatSystemStatus` hardcodes authentication none, branch main, migration version zero, and uses the current request time as build time. The live UI repeats these values. Provider readiness can mean only that configuration exists. This makes incident triage and deployment verification unreliable.

The sole CI workflow builds/publishes containers but does not execute Go tests, vet, races, fresh-database checks, or browser tests. Git tags and images exist, but GitHub release notes do not. The docs still call already-published packaging future work, and the UI backlog still describes some compatibility deletes as no-ops even though the current handler calls persistence.

Evidence: `backend/internal/api/compat.go:84`, `:2436`; `.github/workflows/container-images.yml`; `docs/status.md`; `docs/ui-backlog.md`.

**Acceptance:** embed commit/version/build timestamps, report actual auth and migration state, run tests before image publication, and provide tested install/upgrade/restore instructions and release notes. Verify the deployed image digest instead of trusting the current status response.

### 12. P2 — Dependency maintenance is overdue

`npm audit` reports six affected packages: three high and three moderate. Several concern build tooling or features this SPA may not use; severity counts alone are not proof of production exploitability.

`govulncheck` reports reachable module symbols for [GO-2026-5970](https://pkg.go.dev/vuln/GO-2026-5970) in `golang.org/x/text` and [GO-2026-5004](https://pkg.go.dev/vuln/GO-2026-5004) in `pgx`. No exploit was attempted and reachability does not establish an exploitable request path. The scanner automatically used a newer Go toolchain; these results do not qualify the deployed Go 1.23.12 standard library. The Dockerfile still builds with Go 1.23.

**Acceptance:** update the Go/container baseline and dependencies together, rerun regression checks, and scan the actual shipped images and binaries.

## Product polish

- **Make the primary loop obvious.** Search → choose book/edition → monitor → acquire → import → available should be easy to follow, with one clear next action and a durable explanation when blocked.
- **Simplify search.** The live Moby Dick lookup assigns several original editions and adaptations the same 75% score. Multiple repeated scores, provider labels, raw identities, and evidence blocks demand substantial interpretation. Lead with author, edition, format, language, and cover; place diagnostic evidence behind disclosure.
- **Clarify totals and labels.** The Library showed “6 authors,” “0 monitored,” “3 books,” and “6 shown.” These count different populations without explaining them. “Monitored books” also contains unmonitored/removed entries. Correct membership first, then label the counts consistently.
- **Reduce mobile overhead.** At 390 px the stacked actions, counters, and filters consume most of the first viewport. The table needs horizontal movement for statuses/actions. Keep mobile navigation, but use compact controls and readable book rows/cards.
- **Guide first setup.** Surface authentication, library permissions, provider access, download-client path mapping, and effective automation settings in one verified setup flow. Rich metadata credentials currently require environment configuration.
- **Recover from UI failures.** Add a route-level error boundary with a useful recovery action. Null-list normalization is present, but another rendering or chunk-load exception can still take out the route tree.
- **Keep scope disciplined.** The qBittorrent preferences/category/tracker surfaces already occupy considerable code. Prioritize book acquisition, matching, import recovery, and operator review over more general client administration.

## Recommended execution sequence

1. **Data safety and configuration:** fix payload boundaries, multipart imports, rescan identity, cleanup switches, auth fail-open, and runtime configuration races. Add focused regressions for each.
2. **Prove the book lifecycle:** validate the community Prowlarr fix; qualify Hardcover; test ebook and audiobook acquisition, retries, disconnected clients, restarts, scans, deleted/moved files, and duplicate worker activity against disposable Postgres and controlled legal fixtures. Include backup restore and collections above 200 books.
3. **Polish and ship:** repair query membership and pagination, simplify setup/search/mobile flows, add browser coverage and CI gates, correct operational status/docs, and publish a versioned release with a verified deployment and rollback procedure.

Refactor large files when stabilizing these boundaries rather than expanding feature breadth: `api/compat.go` is 7,880 lines, `api/router.go` 3,424, wanted service/store together exceed 5,000, and library service is 2,535. Extract workflow boundaries with tests around them so changes become easier to reason about.

## Remaining qualification gaps

No fresh Postgres install/upgrade, real Readarr migration, backup restore, authenticated production session, full library scan, Transmission/SABnzbd acquisition, Calibre handoff, or destructive cleanup was run. Full request concurrency and recovery after disk-full/process interruption also remain unqualified. File copying writes directly to the destination and database/file updates are separate operations, so interruption recovery deserves explicit testing. The existing issue [#1](https://github.com/bandoracer/librarry/issues/1) appears addressed by current null normalization and the no-database empty-list checks, but should be closed only after a clean Postgres installation regression test.
